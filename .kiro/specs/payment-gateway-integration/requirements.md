# Requirements Document

## Introduction

This document defines the requirements for the Payment Gateway Integration feature of the commerce-os POS system. The feature adds payment processing capabilities to the existing sales flow, supporting UPI QR payments via Razorpay and debit/credit card payments via Razorpay or Stripe. It covers payment initiation, QR code generation, card payment processing, a payment state machine (pending → success/failure), transaction record storage scoped to a branch, webhook signature verification, retry logic for failed payments, real-time payment status updates via WebSocket, and the payment screen UI in the Next.js dashboard.

This feature integrates with the RBAC spec (Staff role with `sales:create` permission initiates payments), the multi-branch-support spec (all transaction records are scoped to a `branch_id`), and the inventory-management spec (payment confirmation triggers sale completion which drives stock decrement).

---

## Glossary

- **Payment_Service**: The Node.js/Express backend service responsible for payment initiation, status management, webhook handling, and transaction storage.
- **Razorpay**: The primary payment gateway used for UPI QR payments and card payments in the Indian market.
- **Stripe**: The secondary payment gateway used for international debit/credit card payments.
- **UPI**: Unified Payments Interface — an Indian real-time payment system. Payments are initiated by scanning a QR code.
- **QR_Code**: A machine-readable image encoding a UPI payment link, generated by Razorpay and displayed on the payment screen.
- **Payment_Order**: A gateway-side payment record created before the customer pays, identified by a gateway-assigned `payment_order_id`.
- **Transaction**: A system-side record of a payment attempt, stored in PostgreSQL with fields: `transaction_id`, `order_id`, `branch_id`, `business_id`, `amount`, `currency`, `payment_method`, `gateway`, `gateway_payment_id`, `gateway_order_id`, `status`, `failure_reason`, `retry_count`, `created_at`, `updated_at`.
- **Payment_Method**: An enumerated value: `upi` or `card`.
- **Payment_Status**: An enumerated value representing the state of a Transaction: `pending`, `success`, `failed`.
- **Payment_State_Machine**: The set of allowed status transitions for a Transaction: `pending → success`, `pending → failed`, `failed → pending` (on retry).
- **Webhook**: An HTTP POST callback sent by the payment gateway to the Payment_Service to notify of a payment status change.
- **Webhook_Signature**: A cryptographic signature included in the webhook request headers, used to verify the payload originated from the gateway.
- **Retry_Mechanism**: The logic that allows a failed payment to be re-attempted, creating a new Payment_Order while preserving the original Transaction record.
- **WebSocket_Server**: The server-side component that pushes real-time payment status updates to connected Dashboard clients.
- **Payment_Screen**: The Next.js React page displayed during checkout, showing either a QR code (UPI) or a card input form, and real-time payment status.
- **Dashboard**: The existing Next.js React frontend, extended with the Payment_Screen.
- **Order_Service**: The existing Node.js/Express service for order/sales operations, as defined in the multi-branch-support spec.
- **Inventory_Service**: The existing Node.js/Express service for inventory operations, as defined in the inventory-management spec.
- **RBAC_Middleware**: The Express middleware defined in the RBAC spec that enforces role-based permissions.
- **Staff**: The user role defined in the RBAC spec with `sales:create` permission, responsible for initiating payments at the POS.
- **Branch**: A sub-unit of a Business as defined in the multi-branch-support spec, identified by `branch_id`.

## Requirements

### Requirement 1: Payment Initiation

**User Story:** As a Staff member, I want to initiate a payment for an order by selecting a payment method, so that the customer can complete their purchase at the POS.

#### Acceptance Criteria

1. THE Payment_Service SHALL expose a `POST /api/payments/initiate` endpoint that accepts `order_id`, `amount`, `currency`, and `payment_method` (`upi` or `card`) in the request body.
2. WHEN a payment initiation request is received, THE RBAC_Middleware SHALL verify that the authenticated user holds the `sales:create` permission before the Payment_Service processes the request.
3. IF the authenticated user does not hold the `sales:create` permission, THEN THE RBAC_Middleware SHALL return an HTTP 403 response.
4. WHEN a payment initiation request is received, THE Payment_Service SHALL validate that `order_id` references an existing Order within the authenticated user's `branch_id` and `business_id`.
5. IF the `order_id` does not exist or belongs to a different branch, THEN THE Payment_Service SHALL return an HTTP 404 response with a descriptive error message.
6. WHEN a valid initiation request is received, THE Payment_Service SHALL create a Payment_Order on the selected gateway and persist a Transaction record with `status` set to `pending`.
7. THE Payment_Service SHALL scope every Transaction record to the `branch_id` and `business_id` of the authenticated user.
8. WHEN payment initiation succeeds, THE Payment_Service SHALL return the `transaction_id`, `gateway_order_id`, `payment_method`, and any gateway-specific data required by the client (QR code URL for UPI, client secret for card) in the response.

---

### Requirement 2: UPI QR Payment Flow

**User Story:** As a Staff member, I want a UPI QR code to be displayed on the payment screen, so that the customer can scan it and complete payment using any UPI app.

#### Acceptance Criteria

1. WHEN a payment initiation request with `payment_method` set to `upi` is received, THE Payment_Service SHALL call the Razorpay API to create a Payment_Order and retrieve a UPI QR code image URL.
2. THE Payment_Service SHALL return the QR code URL to the client as part of the initiation response so that the Payment_Screen can render it.
3. THE Payment_Screen SHALL display the QR code image within 2 seconds of receiving the initiation response.
4. WHILE a UPI Transaction has `status` set to `pending`, THE Payment_Screen SHALL display the QR code and a waiting indicator.
5. WHEN the Payment_Service receives a webhook from Razorpay confirming UPI payment success, THE Payment_Service SHALL update the Transaction `status` to `success`.
6. WHEN the Transaction `status` changes to `success`, THE WebSocket_Server SHALL emit a `payment_status_updated` event to the connected Payment_Screen client for that transaction.
7. THE Payment_Screen SHALL update the displayed status to "Payment Successful" within 2 seconds of receiving the `payment_status_updated` WebSocket event.

---

### Requirement 3: Card Payment Flow

**User Story:** As a Staff member, I want to process debit and credit card payments through a card input form, so that customers who prefer card payments can complete their purchase.

#### Acceptance Criteria

1. WHEN a payment initiation request with `payment_method` set to `card` is received, THE Payment_Service SHALL create a Payment_Order on Razorpay (primary) or Stripe (secondary) and return a client secret or order token to the Payment_Screen.
2. THE Payment_Screen SHALL render a card input form with fields for card number, expiry date, CVV, and cardholder name when `payment_method` is `card`.
3. THE Payment_Screen SHALL use the gateway's client-side SDK to tokenize card details before transmitting them, so that raw card data is never sent to the Payment_Service.
4. WHEN the customer submits the card form, THE Payment_Screen SHALL submit the tokenized payment to the gateway SDK and await confirmation.
5. WHEN the gateway confirms card payment success, THE Payment_Service SHALL receive a webhook and update the Transaction `status` to `success`.
6. WHEN the Transaction `status` changes to `success`, THE WebSocket_Server SHALL emit a `payment_status_updated` event to the connected Payment_Screen client for that transaction.
7. THE Payment_Screen SHALL update the displayed status to "Payment Successful" within 2 seconds of receiving the `payment_status_updated` WebSocket event.
8. IF the card payment is declined by the gateway, THEN THE Payment_Service SHALL update the Transaction `status` to `failed` and set the `failure_reason` field to the gateway-provided decline reason.

---

### Requirement 4: Payment State Machine

**User Story:** As a system architect, I want payment status transitions to follow a defined state machine, so that Transactions are never left in an inconsistent state.

#### Acceptance Criteria

1. THE Payment_Service SHALL initialize every new Transaction with `status` set to `pending`.
2. THE Payment_Service SHALL allow the following status transitions only: `pending → success`, `pending → failed`, and `failed → pending` (when a retry is initiated).
3. IF a request attempts to transition a Transaction to a status not permitted by the Payment_State_Machine, THEN THE Payment_Service SHALL return an HTTP 409 response with a descriptive error message.
4. WHEN a Transaction transitions to `success`, THE Payment_Service SHALL record the `updated_at` timestamp in UTC.
5. WHEN a Transaction transitions to `failed`, THE Payment_Service SHALL record the `updated_at` timestamp in UTC and persist the `failure_reason` provided by the gateway.
6. THE Payment_Service SHALL perform all status transition writes within a database transaction to prevent partial updates.

---

### Requirement 5: Transaction Record Storage

**User Story:** As an Owner, I want all payment transactions to be stored with full details, so that I can audit payments, reconcile accounts, and investigate disputes.

#### Acceptance Criteria

1. THE Payment_Service SHALL persist every Transaction to PostgreSQL with the following fields: `transaction_id` (UUID), `order_id`, `branch_id`, `business_id`, `amount`, `currency`, `payment_method`, `gateway`, `gateway_payment_id`, `gateway_order_id`, `status`, `failure_reason`, `retry_count`, `created_at`, `updated_at`.
2. THE Payment_Service SHALL enforce that `branch_id` and `business_id` are non-nullable on every Transaction record.
3. THE Payment_Service SHALL expose a `GET /api/payments/transactions` endpoint that returns paginated Transaction records filtered by `branch_id`, with optional filters for `status`, `payment_method`, and date range.
4. WHEN a list request is received, THE RBAC_Middleware SHALL verify that the authenticated user has the `sales:read` permission before returning Transaction records.
5. THE Payment_Service SHALL expose a `GET /api/payments/transactions/:transaction_id` endpoint that returns a single Transaction record.
6. IF a request targets a Transaction that belongs to a different `branch_id` than the authenticated user's branch, THEN THE Payment_Service SHALL return an HTTP 403 response.
7. THE Payment_Service SHALL store Transaction records as immutable entries after reaching a terminal state (`success`); terminal Transaction records SHALL NOT be modified via the API.

---

### Requirement 6: Webhook Handling and Signature Verification

**User Story:** As a security engineer, I want all incoming webhooks to be verified using the gateway's signature before processing, so that fraudulent or tampered webhook payloads are rejected.

#### Acceptance Criteria

1. THE Payment_Service SHALL expose a `POST /api/payments/webhook/razorpay` endpoint and a `POST /api/payments/webhook/stripe` endpoint to receive gateway callbacks.
2. WHEN a webhook request is received, THE Payment_Service SHALL verify the webhook signature using the gateway-provided secret key before processing the payload.
3. THE Payment_Service SHALL verify Razorpay webhooks by computing an HMAC-SHA256 of the raw request body using the Razorpay webhook secret and comparing it to the `X-Razorpay-Signature` header value.
4. THE Payment_Service SHALL verify Stripe webhooks using the Stripe SDK's `constructEvent` method with the raw request body and the `Stripe-Signature` header.
5. IF the webhook signature verification fails, THEN THE Payment_Service SHALL return an HTTP 400 response and log the failure without updating any Transaction record.
6. WHEN a verified webhook payload indicates payment success, THE Payment_Service SHALL look up the Transaction by `gateway_order_id` and transition its status to `success`.
7. WHEN a verified webhook payload indicates payment failure, THE Payment_Service SHALL look up the Transaction by `gateway_order_id` and transition its status to `failed`, persisting the `failure_reason`.
8. THE Payment_Service SHALL return an HTTP 200 response to the gateway within 5 seconds of receiving a webhook to prevent gateway retry storms.
9. THE Payment_Service SHALL process webhook payloads idempotently: if a webhook for an already-terminal Transaction is received, THE Payment_Service SHALL return HTTP 200 without modifying the Transaction.

---

### Requirement 7: Retry Mechanism for Failed Payments

**User Story:** As a Staff member, I want to retry a failed payment without creating a new order, so that the customer can attempt payment again without losing their cart.

#### Acceptance Criteria

1. THE Payment_Service SHALL expose a `POST /api/payments/:transaction_id/retry` endpoint that initiates a new payment attempt for a Transaction with `status` set to `failed`.
2. WHEN a retry request is received, THE Payment_Service SHALL transition the Transaction `status` from `failed` to `pending` and increment the `retry_count` field by 1.
3. THE Payment_Service SHALL enforce a maximum `retry_count` of 3 per Transaction.
4. IF a retry request is received for a Transaction whose `retry_count` has reached 3, THEN THE Payment_Service SHALL return an HTTP 422 response with a descriptive error message.
5. IF a retry request is received for a Transaction with `status` other than `failed`, THEN THE Payment_Service SHALL return an HTTP 409 response.
6. WHEN a retry is initiated, THE Payment_Service SHALL create a new Payment_Order on the gateway and return updated gateway data (new QR code URL for UPI, new client secret for card) to the client.
7. THE Payment_Screen SHALL display the updated QR code or card form upon receiving the retry response, without requiring a full page reload.

---

### Requirement 8: Sale Completion and Inventory Integration

**User Story:** As a system architect, I want payment confirmation to trigger sale completion, so that stock is decremented only after a payment is confirmed as successful.

#### Acceptance Criteria

1. WHEN a Transaction transitions to `success`, THE Payment_Service SHALL call the Order_Service to mark the associated Order as completed.
2. WHEN the Order_Service marks an Order as completed, THE Inventory_Service SHALL decrement stock quantities for all items in that Order as defined in the inventory-management spec Requirement 3.
3. THE Payment_Service SHALL perform the Transaction status update and the Order completion call within a single database transaction so that a partial update does not leave the Order in an inconsistent state.
4. IF the Order completion call fails, THEN THE Payment_Service SHALL roll back the Transaction status update and return an HTTP 500 response, preserving the Transaction in `pending` status for retry.
5. WHEN a Transaction transitions to `failed`, THE Payment_Service SHALL NOT mark the associated Order as completed and SHALL NOT trigger stock decrement.

---

### Requirement 9: Real-Time Payment Status Updates

**User Story:** As a Staff member, I want the payment screen to update in real time when a payment is confirmed or fails, so that I can immediately inform the customer and proceed with the next action.

#### Acceptance Criteria

1. THE WebSocket_Server SHALL accept authenticated WebSocket connections from Payment_Screen clients, validating the Access_Token on connection establishment.
2. WHEN a Transaction status changes, THE WebSocket_Server SHALL emit a `payment_status_updated` event containing `transaction_id`, `status`, and `failure_reason` (if applicable) to the client subscribed to that transaction.
3. THE Payment_Screen SHALL subscribe to the `payment_status_updated` event for the active `transaction_id` immediately after payment initiation.
4. THE Payment_Screen SHALL update the displayed payment status within 2 seconds of receiving a `payment_status_updated` WebSocket event.
5. IF a WebSocket connection is not available or is lost, THE Payment_Screen SHALL fall back to polling `GET /api/payments/transactions/:transaction_id` at an interval of 3 seconds.
6. WHEN the Transaction `status` is `success`, THE Payment_Screen SHALL display a success confirmation and provide a button to proceed to the next sale.
7. WHEN the Transaction `status` is `failed`, THE Payment_Screen SHALL display the `failure_reason` and provide a "Retry Payment" button that calls the retry endpoint.

---

### Requirement 10: Payment Screen UI

**User Story:** As a Staff member, I want a clear payment screen that shows the correct payment interface for the selected method and updates in real time, so that I can guide the customer through checkout efficiently.

#### Acceptance Criteria

1. THE Payment_Screen SHALL display a payment method selector allowing the Staff member to choose between `upi` and `card` before initiating payment.
2. WHEN `upi` is selected and payment is initiated, THE Payment_Screen SHALL display the QR code image, the payment amount, and a "Waiting for payment" status indicator.
3. WHEN `card` is selected and payment is initiated, THE Payment_Screen SHALL display a card input form with fields for card number, expiry date, CVV, and cardholder name.
4. THE Payment_Screen SHALL display the order total and itemized line items alongside the payment interface so that the Staff member can confirm the amount with the customer.
5. WHILE a Transaction has `status` set to `pending`, THE Payment_Screen SHALL display a loading or waiting indicator and disable the payment method selector.
6. WHEN a Transaction reaches a terminal status (`success` or `failed`), THE Payment_Screen SHALL remove the waiting indicator and display the outcome clearly.
7. THE Payment_Screen SHALL be accessible only to authenticated users with the `sales:create` permission; unauthenticated users SHALL be redirected to the login page.
8. IF the payment initiation API call fails, THEN THE Payment_Screen SHALL display a descriptive error message and allow the Staff member to retry the initiation without reloading the page.

---

### Requirement 11: REST API for Payment Operations

**User Story:** As a developer, I want a complete REST API for payment operations, so that the Dashboard and other services can integrate with the payment module.

#### Acceptance Criteria

1. THE Payment_Service SHALL expose the following endpoints:
   - `POST /api/payments/initiate` — initiate a payment (requires `sales:create`)
   - `POST /api/payments/:transaction_id/retry` — retry a failed payment (requires `sales:create`)
   - `GET /api/payments/transactions` — list transactions for a branch (requires `sales:read`)
   - `GET /api/payments/transactions/:transaction_id` — get a transaction by ID (requires `sales:read`)
   - `POST /api/payments/webhook/razorpay` — receive Razorpay webhook callbacks (no auth, signature-verified)
   - `POST /api/payments/webhook/stripe` — receive Stripe webhook callbacks (no auth, signature-verified)
2. THE Payment_Service SHALL require a valid JWT Access_Token on all endpoints except the webhook endpoints.
3. IF a request is made to a non-webhook endpoint without a valid JWT token, THEN THE RBAC_Middleware SHALL return an HTTP 401 response.
4. THE Payment_Service SHALL return all responses in JSON format with a consistent envelope structure containing `data`, `error`, and `meta` fields.
5. THE Payment_Service SHALL support pagination on list endpoints via `page` and `limit` query parameters, with a maximum limit of 100 records per page.
6. THE Payment_Service SHALL scope all transaction queries to the `branch_id` of the authenticated user, consistent with the data isolation guarantee defined in the multi-branch-support spec Requirement 9.
