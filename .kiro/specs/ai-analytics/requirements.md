# Requirements Document

## Introduction

This document defines the requirements for the AI-Powered Analytics module of the commerce-os POS system. The module introduces a Python FastAPI microservice that hosts machine learning models for sales forecasting, product demand prediction, and customer behavior segmentation. It integrates with the OpenAI API to generate natural-language insights and to support a natural-language query interface. A Next.js analytics dashboard renders charts and AI-generated insights. All analytics data is sourced from the existing PostgreSQL database (transactions from the payment-gateway-integration spec, stock data from the inventory-management spec) and is scoped to `branch_id` consistent with the multi-branch-support spec. Access to analytics requires the `reports:read` permission, which is held exclusively by the `owner` role per the RBAC spec.

This feature integrates with:
- **inventory-management spec**: Products (stock_quantity, reorder_level) and Stock_Logs are the data source for demand prediction and restock recommendations.
- **payment-gateway-integration spec**: Transactions (amount, payment_method, status, timestamp) are the data source for sales forecasting.
- **multi-branch-support spec**: All analytics are scoped to `branch_id`; Central Admin (Owner) may request cross-branch analytics.
- **RBAC spec**: The `reports:read` permission (Owner only) gates all analytics endpoints and the analytics dashboard UI.

## Glossary

- **Analytics_Service**: The Python FastAPI microservice that hosts ML models, calls the OpenAI API, and exposes analytics endpoints consumed by the Node.js backend proxy.
- **Analytics_Proxy**: The Node.js/Express middleware layer that forwards authenticated analytics requests from the frontend to the Analytics_Service, enforcing RBAC before proxying.
- **Analytics_Dashboard**: The Next.js React page that renders charts, KPI cards, AI-generated insights, and the natural-language query interface.
- **Forecasting_Model**: The time-series ML model (e.g., Prophet or ARIMA) hosted in the Analytics_Service that predicts future sales revenue.
- **Demand_Model**: The ML model hosted in the Analytics_Service that predicts per-product demand over a future time window.
- **Segmentation_Model**: The Analytics_Service component that classifies customers as `new` or `repeat` based on transaction history.
- **OpenAI_Client**: The Analytics_Service component that calls the OpenAI Chat Completions API to generate natural-language insights and to interpret natural-language queries.
- **NL_Query_Interface**: The Analytics_Dashboard UI component that accepts a free-text question from the user and displays an AI-generated answer.
- **Insight**: A short natural-language summary generated by the OpenAI_Client describing a trend, anomaly, or recommendation derived from analytics data.
- **Recommendation**: A structured data object produced by the Analytics_Service containing either a best-selling item list or a restock alert list.
- **Data_Pipeline**: The scheduled process that extracts sales and inventory data from PostgreSQL and makes it available to the Analytics_Service for model inference.
- **Branch**: A sub-unit of a Business as defined in the multi-branch-support spec, identified by `branch_id`.
- **Owner**: The user role defined in the RBAC spec that holds the `reports:read` permission and is the only role permitted to access analytics.
- **Staff**: The user role defined in the RBAC spec; Staff users do not hold `reports:read` and SHALL NOT access analytics endpoints or the Analytics_Dashboard.
- **RBAC_Middleware**: The Express middleware defined in the RBAC spec that enforces role-based permissions on the Analytics_Proxy routes.
- **Transaction**: A payment record as defined in the payment-gateway-integration spec, with fields: `transaction_id`, `order_id`, `branch_id`, `amount`, `status`, `created_at`.
- **Product**: An inventory record as defined in the inventory-management spec, with fields: `product_id`, `name`, `stock_quantity`, `reorder_level`.
- **Stock_Log**: An immutable stock movement record as defined in the inventory-management spec.

## Requirements

### Requirement 1: Analytics Microservice Architecture

**User Story:** As a system architect, I want a dedicated Python FastAPI microservice for ML and AI operations, so that the analytics workload is isolated from the existing Node.js backend and can be scaled independently.

#### Acceptance Criteria

1. THE Analytics_Service SHALL be implemented as a Python FastAPI application running on a configurable port (default: 8001).
2. THE Analytics_Service SHALL expose a health-check endpoint at `GET /health` that returns HTTP 200 with service status and model readiness flags.
3. THE Analytics_Proxy SHALL expose analytics routes under `/api/analytics/` in the existing Node.js/Express application and forward requests to the Analytics_Service after RBAC validation.
4. WHEN the Analytics_Proxy forwards a request, THE Analytics_Proxy SHALL attach the authenticated user's `business_id`, `branch_id`, and `role` as HTTP headers (`X-Business-ID`, `X-Branch-ID`, `X-User-Role`) so the Analytics_Service can apply data scoping without re-validating the JWT.
5. THE Analytics_Service SHALL read data exclusively from the PostgreSQL database using a read-only connection pool, and SHALL NOT write to any table owned by other modules.
6. IF the Analytics_Service is unavailable, THEN THE Analytics_Proxy SHALL return an HTTP 503 response with a descriptive error message rather than timing out silently.
7. THE Analytics_Service SHALL support CORS only for requests originating from the Analytics_Proxy; direct browser access to the Analytics_Service SHALL be rejected.

### Requirement 2: Data Pipeline

**User Story:** As a data engineer, I want sales and inventory data to be extracted from PostgreSQL and made available to the ML models, so that forecasts and predictions are based on current data.

#### Acceptance Criteria

1. THE Data_Pipeline SHALL query the `transactions` table (filtered by `branch_id` and `status = 'success'`) and the `products` and `stock_logs` tables to assemble training and inference datasets.
2. THE Data_Pipeline SHALL aggregate daily sales totals per `branch_id` from Transaction records for use by the Forecasting_Model.
3. THE Data_Pipeline SHALL aggregate per-product sales quantities per `branch_id` from Stock_Log records with `action_type = 'SALE'` for use by the Demand_Model.
4. THE Data_Pipeline SHALL extract per-customer transaction counts per `branch_id` to support the Segmentation_Model, using `order_id` to link Transactions to customer identifiers.
5. WHEN a data extraction query is executed, THE Data_Pipeline SHALL scope all queries to the `branch_id` provided in the request context.
6. THE Analytics_Service SHALL support on-demand data extraction triggered by an analytics API request, with results cached in memory for a configurable TTL (default: 15 minutes) to avoid redundant database queries within the same window.
7. IF a data extraction query returns fewer than 30 days of Transaction records for a given `branch_id`, THEN THE Analytics_Service SHALL include a `data_quality_warning` field in the response indicating insufficient historical data.

### Requirement 3: Sales Forecasting

**User Story:** As an Owner, I want to see a sales forecast for the next 7 and 30 days, so that I can plan staffing, purchasing, and promotions based on predicted revenue.

#### Acceptance Criteria

1. THE Analytics_Service SHALL expose a `GET /analytics/forecast/sales` endpoint that accepts `branch_id`, `horizon_days` (7 or 30), and an optional `start_date` parameter.
2. WHEN a sales forecast request is received, THE Forecasting_Model SHALL use at least 30 days of historical daily sales totals for the given `branch_id` to generate a forecast.
3. THE Forecasting_Model SHALL return a forecast as a time-series array of objects, each containing `date` (ISO 8601) and `predicted_revenue` (numeric, in the branch's currency).
4. THE Analytics_Service SHALL include a `confidence_interval` object with `lower` and `upper` bounds for each forecast data point.
5. WHEN a forecast is generated, THE OpenAI_Client SHALL produce a one-paragraph Insight summarizing the forecast trend (e.g., growth, decline, seasonality) and append it to the response as an `insight` field.
6. IF fewer than 30 days of historical data are available for the requested `branch_id`, THEN THE Analytics_Service SHALL return the forecast with a `data_quality_warning` and SHALL NOT suppress the response entirely.
7. THE Analytics_Dashboard SHALL render the sales forecast as a line chart with confidence interval bands and display the AI-generated Insight below the chart.

---

### Requirement 4: Product Demand Prediction

**User Story:** As an Owner, I want to see predicted demand for each product over the next 7 and 30 days, so that I can make informed purchasing and stocking decisions.

#### Acceptance Criteria

1. THE Analytics_Service SHALL expose a `GET /analytics/forecast/demand` endpoint that accepts `branch_id`, `horizon_days` (7 or 30), and an optional `product_id` filter.
2. WHEN a demand prediction request is received, THE Demand_Model SHALL use per-product sales quantity history from Stock_Log records with `action_type = 'SALE'` for the given `branch_id`.
3. THE Demand_Model SHALL return a list of per-product demand forecasts, each containing `product_id`, `product_name`, `predicted_quantity`, and `confidence_interval`.
4. THE Analytics_Service SHALL rank the returned products by `predicted_quantity` in descending order by default.
5. WHEN demand predictions are generated, THE OpenAI_Client SHALL produce an Insight identifying the top 3 products by predicted demand and any products showing a significant demand decline.
6. IF a product has fewer than 14 days of sales history, THEN THE Analytics_Service SHALL include a `data_quality_warning` for that product's forecast entry and SHALL still return a best-effort prediction.
7. THE Analytics_Dashboard SHALL render demand predictions as a bar chart grouped by product and display the AI-generated Insight.

---

### Requirement 5: Customer Behavior Segmentation

**User Story:** As an Owner, I want to see a breakdown of new versus repeat customers, so that I can evaluate customer retention and tailor marketing efforts.

#### Acceptance Criteria

1. THE Analytics_Service SHALL expose a `GET /analytics/customers/segmentation` endpoint that accepts `branch_id` and an optional `date_range` (start and end date in ISO 8601 format).
2. WHEN a segmentation request is received, THE Segmentation_Model SHALL classify each customer as `new` (first transaction within the business) or `repeat` (more than one transaction within the business) based on Transaction history scoped to `branch_id`.
3. THE Analytics_Service SHALL return a segmentation summary containing: `total_customers`, `new_customers` (count and percentage), `repeat_customers` (count and percentage), and `repeat_purchase_rate`.
4. THE Analytics_Service SHALL return a time-series breakdown of new vs. repeat customer counts aggregated by week within the requested date range.
5. WHEN segmentation data is computed, THE OpenAI_Client SHALL produce an Insight commenting on the repeat purchase rate trend and suggesting retention actions if the repeat rate is below 30%.
6. THE Analytics_Dashboard SHALL render the segmentation summary as a donut chart and the time-series breakdown as a stacked bar chart, with the AI-generated Insight displayed alongside.

---

### Requirement 6: Best-Selling Items Recommendation

**User Story:** As an Owner, I want to see a ranked list of best-selling products, so that I can prioritize promotions and ensure adequate stock for high-demand items.

#### Acceptance Criteria

1. THE Analytics_Service SHALL expose a `GET /analytics/recommendations/best-sellers` endpoint that accepts `branch_id`, `limit` (default: 10, maximum: 50), and `period_days` (default: 30).
2. WHEN a best-sellers request is received, THE Analytics_Service SHALL rank products by total quantity sold within the specified `period_days` for the given `branch_id`, using Stock_Log records with `action_type = 'SALE'`.
3. THE Analytics_Service SHALL return a list of Recommendation objects, each containing: `product_id`, `product_name`, `total_quantity_sold`, `total_revenue`, and `rank`.
4. WHEN best-seller data is computed, THE OpenAI_Client SHALL produce an Insight highlighting the top product and any notable trends (e.g., a product that entered the top 5 this period).
5. THE Analytics_Dashboard SHALL render the best-sellers list as a ranked table with revenue and quantity columns, and display the AI-generated Insight.

---

### Requirement 7: Restock Recommendations

**User Story:** As an Owner, I want to see a list of products that need restocking based on current stock levels and predicted demand, so that I can place purchase orders before stockouts occur.

#### Acceptance Criteria

1. THE Analytics_Service SHALL expose a `GET /analytics/recommendations/restock` endpoint that accepts `branch_id` and an optional `horizon_days` (default: 7).
2. WHEN a restock request is received, THE Analytics_Service SHALL identify products where `stock_quantity` is less than the product's `reorder_level` OR where `stock_quantity` is less than the `predicted_quantity` from the Demand_Model for the given `horizon_days`.
3. THE Analytics_Service SHALL return a list of Recommendation objects, each containing: `product_id`, `product_name`, `current_stock`, `reorder_level`, `predicted_demand`, `suggested_restock_quantity`, and `urgency` (`critical` if stock_quantity = 0, `high` if stock_quantity < reorder_level, `medium` otherwise).
4. THE Analytics_Service SHALL sort the restock list by `urgency` (critical first, then high, then medium) and then by `predicted_demand` descending within each urgency tier.
5. WHEN restock recommendations are generated, THE OpenAI_Client SHALL produce an Insight summarizing the number of critical and high-urgency items and recommending immediate action for critical items.
6. THE Analytics_Dashboard SHALL render the restock list as a table with urgency badges and display the AI-generated Insight.

---

### Requirement 8: Natural Language Query Interface

**User Story:** As an Owner, I want to ask questions about my business data in plain English, so that I can get quick answers without navigating multiple dashboard views.

#### Acceptance Criteria

1. THE Analytics_Service SHALL expose a `POST /analytics/query` endpoint that accepts a `question` (free-text string, maximum 500 characters) and `branch_id` in the request body.
2. WHEN a natural-language query is received, THE OpenAI_Client SHALL construct a prompt that includes the question, a summary of available analytics data for the given `branch_id`, and instructions to respond with structured JSON containing `answer` (natural-language string) and `chart_data` (optional structured data for visualization).
3. THE OpenAI_Client SHALL use the OpenAI Chat Completions API with a model configurable via environment variable (default: `gpt-4o-mini`).
4. THE Analytics_Service SHALL return the OpenAI_Client response as a JSON object containing `answer`, optional `chart_data`, and `query_interpreted` (the Analytics_Service's interpretation of the question).
5. IF the OpenAI API call fails or times out after 10 seconds, THEN THE Analytics_Service SHALL return an HTTP 503 response with a descriptive error message and SHALL NOT return a partial or fabricated answer.
6. THE NL_Query_Interface SHALL display a text input field and a submit button; WHEN a response is received, THE NL_Query_Interface SHALL render the `answer` as formatted text and, if `chart_data` is present, render an appropriate chart.
7. THE Analytics_Service SHALL sanitize the `question` input by stripping HTML tags and truncating to 500 characters before passing it to the OpenAI_Client, to prevent prompt injection.
8. THE Analytics_Service SHALL log each NL query (question text, `branch_id`, response latency, and success/failure) for operational monitoring, without logging the full OpenAI response body.

### Requirement 9: Analytics Dashboard UI

**User Story:** As an Owner, I want a dedicated analytics dashboard page with charts and AI insights, so that I can monitor business performance at a glance.

#### Acceptance Criteria

1. THE Analytics_Dashboard SHALL be accessible at the `/analytics` route in the Next.js application and SHALL be rendered only for authenticated users with the `reports:read` permission.
2. IF an authenticated user without the `reports:read` permission navigates to `/analytics`, THEN THE Analytics_Dashboard SHALL redirect the user to the home page.
3. THE Analytics_Dashboard SHALL display the following sections: Sales Forecast, Product Demand, Customer Segmentation, Best Sellers, Restock Recommendations, and Natural Language Query.
4. THE Analytics_Dashboard SHALL use the active Branch_Context (from the multi-branch-support spec branch switcher) as the `branch_id` for all analytics API calls.
5. WHILE a Central_Admin (Owner) is viewing the Analytics_Dashboard, THE Analytics_Dashboard SHALL provide a toggle to switch between branch-scoped view and cross-branch aggregated view.
6. THE Analytics_Dashboard SHALL display a loading skeleton for each section while data is being fetched, and SHALL display a descriptive error message if a section's API call fails.
7. WHEN the branch context changes, THE Analytics_Dashboard SHALL re-fetch all analytics data for the newly selected branch.
8. THE Analytics_Dashboard SHALL display `data_quality_warning` messages returned by the Analytics_Service as inline notices within the affected chart section.

---

### Requirement 10: Cross-Branch Analytics for Owner

**User Story:** As an Owner (Central Admin), I want to view aggregated analytics across all branches, so that I can compare branch performance and make business-wide decisions.

#### Acceptance Criteria

1. THE Analytics_Service SHALL accept `branch_id = 'all'` on all analytics endpoints when the request carries `X-User-Role: owner`, and SHALL aggregate data across all branches belonging to the `business_id`.
2. WHEN `branch_id = 'all'` is requested by a non-owner role, THE Analytics_Proxy SHALL return an HTTP 403 response before forwarding the request to the Analytics_Service.
3. THE Analytics_Service SHALL return per-branch breakdowns alongside the aggregated totals when `branch_id = 'all'` is requested, so that the Analytics_Dashboard can render a comparison view.
4. THE Analytics_Dashboard SHALL render a branch comparison bar chart when cross-branch data is returned, showing each branch's contribution to the aggregated metric.

---

### Requirement 11: Permission Model and API Security

**User Story:** As a security engineer, I want all analytics endpoints to be protected by the existing RBAC permission model, so that only authorized Owners can access sensitive business analytics.

#### Acceptance Criteria

1. THE RBAC_Middleware SHALL require the `reports:read` permission on all routes under `/api/analytics/`.
2. IF a request to any `/api/analytics/` route is made by a user without the `reports:read` permission, THEN THE RBAC_Middleware SHALL return an HTTP 403 response.
3. IF a request to any `/api/analytics/` route is made without a valid JWT Access_Token, THEN THE RBAC_Middleware SHALL return an HTTP 401 response.
4. THE Analytics_Proxy SHALL scope all forwarded requests to the `business_id` of the authenticated user, so that the Analytics_Service never receives a request without a valid business scope.
5. THE Analytics_Service SHALL validate that the `branch_id` in each request belongs to the `business_id` provided in the `X-Business-ID` header, and SHALL return an HTTP 403 response if the branch does not belong to the business.
6. THE Analytics_Service SHALL not expose any endpoint that allows writing to or modifying data in the PostgreSQL database.

---

### Requirement 12: REST API for Analytics Operations

**User Story:** As a developer, I want a complete REST API for analytics operations, so that the Analytics_Dashboard and other consumers can integrate with the analytics module.

#### Acceptance Criteria

1. THE Analytics_Proxy SHALL expose the following endpoints (all require `reports:read` permission):
   - `GET /api/analytics/forecast/sales` — sales forecast for a branch
   - `GET /api/analytics/forecast/demand` — product demand predictions for a branch
   - `GET /api/analytics/customers/segmentation` — customer segmentation summary
   - `GET /api/analytics/recommendations/best-sellers` — best-selling products list
   - `GET /api/analytics/recommendations/restock` — restock recommendations list
   - `POST /api/analytics/query` — natural-language query interface
   - `GET /api/analytics/health` — proxy health check (no auth required)
2. THE Analytics_Proxy SHALL return all responses in JSON format with a consistent envelope structure containing `data`, `error`, and `meta` fields, matching the convention used by other modules.
3. THE Analytics_Proxy SHALL support pagination on list endpoints (`best-sellers`, `restock`) via `page` and `limit` query parameters, with a maximum limit of 100 records per page.
4. THE Analytics_Service SHALL return HTTP 400 with a descriptive error message when required query parameters (`branch_id`, `horizon_days`) are missing or invalid.
5. THE Analytics_Service SHALL include a `generated_at` ISO 8601 timestamp in every response so that the Analytics_Dashboard can display data freshness to the user.
